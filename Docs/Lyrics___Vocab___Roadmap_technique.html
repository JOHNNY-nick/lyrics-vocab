Architecture retenue : le backend FastAPI, PostgreSQL et Ollama tournent sur ton PC. Tailscale (réseau privé chiffré) rend ce PC joignable depuis ton téléphone en Wi-Fi comme en données mobiles, sans rien exposer sur Internet. PC : application web installable (PWA), avec une icône dans la barre des tâches. Mobile : application Android (.apk). Les deux utilisent la même base. Sur mobile, l'app reste utilisable sans connexion et se synchronise avec la base à la reconnexion (étape 08b). Pas de compte ni d'hébergeur : seuls tes appareils du réseau Tailscale peuvent joindre l'API.

Pourquoi ce découpage : chaque dossier a une seule responsabilité (routers = HTTP, services = logique métier/API externes, models = schéma DB), ce qui permet de tester services/ indépendamment des routes, et de remplacer un client externe (ex. changer de fournisseur de traduction) sans toucher au reste. Côté Flutter, séparer screens/ de providers/ évite de mélanger l'état de l'app et l'affichage — un écran ne fait que lire un provider et afficher.

Dépôt Git : un seul dépôt racine avec les dossiers backend/ et app/, et un .gitignore commun excluant .env, /backend/.venv et /app/build.
Comment fonctionne l'application

Vue d'ensemble du parcours, du mot tapé par l'utilisateur jusqu'au rappel de révision, avec les services qui interviennent à chaque étape.

PWA (PC) + App Android (.apk) → FastAPI (ton PC, via Tailscale) │ ┌─────────────────┼─────────────────┐ ▼ ▼ ▼ Musixmatch DeepL Ollama (local) (extrait lyrics) (traduction) (explication argot) │ │ │ └─────────────────┼─────────────────┘ ▼ PostgreSQL (cache : mot, extrait, traduction, explication, planning SM-2) │ ▼ Fiche affichée dans l'app + entrée dans le planning de révision
1
L'utilisateur ajoute un mot
Depuis la PWA sur PC ou l'app Android, il tape un mot ou une expression rencontrée dans une chanson. La requête part vers le backend FastAPI de ton PC, via Tailscale, en Wi-Fi comme en données mobiles. Si le téléphone n'a pas de réseau ou ne joint pas le PC, le mot est enregistré en local et sera envoyé plus tard (voir étape 10).
2
Le backend vérifie le cache
Si ce mot a déjà été recherché, la fiche (extrait + traduction + explication) est renvoyée directement depuis PostgreSQL, sans réappeler aucune API externe.
3
Sinon, recherche de l'extrait
Le backend interroge Musixmatch, morceau par morceau, parmi les artistes préférés de l'utilisateur, jusqu'à trouver une occurrence du mot ; il en extrait 1 à 2 lignes.
4
Traduction puis explication
DeepL traduit le mot en français ; Ollama (sur ton PC) génère une explication courte du sens en contexte (argot, double sens). Sinon, seule la traduction DeepL est utilisée.
5
Mise en cache
Le résultat complet (extrait, traduction, explication) est stocké en base pour ce mot, afin de ne plus jamais refaire les mêmes appels externes.
6
Entrée dans le planning de révision
Le mot est ajouté à la table revision avec une première date de rappel, calculée par l'algorithme SM-2.
7
Rappel à l'ouverture de l'app
À chaque lancement, l'app affiche l'écran « Révisions du jour » avec les mots dont la date de rappel est atteinte (sur Android, une notification locale peut aussi le rappeler, même hors-ligne).
8
Réponse de l'utilisateur
L'utilisateur indique s'il se souvenait du mot ou non ; SM-2 recalcule le prochain intervalle (plus long si su, plus court sinon) et met à jour la base.
9
Mode hors-ligne (mobile)
Sans connexion, l'app Android lit le cache local Hive : fiches, bibliothèque et révisions du jour restent utilisables. Les actions faites (réponses de révision, mots ajoutés) sont mises dans une file d'attente locale.
10
Synchronisation à la reconnexion
Dès que le téléphone retrouve le réseau et ton PC, l'app envoie la file d'attente au backend, qui l'applique à la base commune (SM-2 recalculé, mots en attente enrichis), puis renvoie les changements faits depuis l'autre appareil. Un mot ajouté sur le PC apparaît sur le téléphone, et inversement.

Concepts à maîtriser
User stories
Formuler le besoin sous forme « en tant qu'utilisateur, je veux… afin de… » pour chaque fonctionnalité clé (ajout de mot, réception de rappel, révision).
Scope MVP
Geler un périmètre volontairement étroit : 1 mot → 1 définition FR → 1 à 3 extraits → 1 planning de rappel. Tout le reste devient « v2 ».
Jeu de test personnel
Lister 15–20 mots/expressions réellement difficiles à retenir, et 5–10 artistes préférés. Ce jeu sert de test tout au long du build.

Frontend : Flutter Web (PWA) pour le PC, Flutter Android (.apk) pour le mobile
Flutter retenu car un seul projet produit les deux clients : la cible web (PWA installable sur PC) et la cible Android (.apk), avec le même code Dart. On commence par la cible web pour itérer vite en local, puis on ajoute la cible Android à l'étape 08bis une fois le backend en ligne.

FastAPI choisi pour son typage (Pydantic), sa documentation Swagger générée automatiquement, et sa simplicité pour appeler des API externes en asynchrone.

Relationnel, adapté aux liens mot↔extrait↔révision. Installé en local sur ton PC : aucune base en ligne, aucun hébergeur.

Concepts à maîtriser
Pourquoi c'est structurant
Les paroles complètes sont protégées. L'app ne doit jamais stocker ou afficher une chanson entière — seulement de courts extraits (1–2 lignes) autour du mot recherché, générés à la demande.
Vérification préalable de l'accès Musixmatch
L'accès développeur à Musixmatch s'est resserré ces dernières années (quotas réduits, extraits parfois tronqués, certains endpoints réservés aux partenaires). Avant d'engager la semaine 05, créer un compte développeur, obtenir une clé de test et vérifier concrètement les limites actuelles du plan gratuit plutôt que de le supposer.
Musixmatch API — extraits courts
Conçue pour des snippets, avec un quota gratuit pour usage personnel/développeur. Endpoint principal pour rechercher une occurrence de mot dans un morceau.
GET /matcher.lyrics.get
Genius API — métadonnées uniquement

Architecture : le backend, PostgreSQL et Ollama restent sur ton PC. Tailscale relie le PC et le téléphone dans un réseau privé : le téléphone joint le PC en Wi-Fi comme en données mobiles, et rien n'est exposé sur Internet. Pas d'hébergeur, pas de compte applicatif. À faire dès que le parcours fonctionne en local (étape 07) et avant l'APK (08b).
Concepts à maîtriser
Comment fonctionne Tailscale
Tailscale crée un réseau privé chiffré (un « tailnet ») entre tes appareils. Chacun reçoit une adresse stable et un nom (MagicDNS), par exemple mon-pc.tailXXXX.ts.net. Le téléphone, qu'il soit en Wi-Fi ou en 4G/5G, joint le PC tant que l'application Tailscale y est active. Seuls les appareils connectés à ton compte Tailscale peuvent atteindre le PC : c'est ce qui remplace l'authentification de l'application.
Installation et compte
Installer Tailscale sur le PC (Windows) et sur le téléphone Android, avec le même compte. Vérifier les conditions du plan personnel gratuit sur le site de Tailscale. Dans la console d'administration, désactiver l'expiration de clé du PC : sinon l'accès peut se couper au bout d'une durée par défaut, que tu ne verrais qu'au moment où l'app ne se synchronise plus. Sur Android, un seul VPN peut être actif à la fois : si tu en utilises un autre, il devra être désactivé.
HTTPS sur le réseau privé
Activer MagicDNS et les certificats HTTPS dans la console d'administration, puis exposer le backend avec tailscale serve. HTTPS est nécessaire pour que la PWA s'enregistre comme application installable. La syntaxe exacte de la commande varie selon la version de Tailscale : vérifier avec tailscale serve --help. Ne pas utiliser « Funnel », qui exposerait le service à tout Internet.
tailscale serve https / http://localhost:8000
Servir la PWA depuis FastAPI
FastAPI sert à la fois l'API (sous le préfixe /api) et le build web de Flutter (fichiers statiques à la racine). Une seule adresse, une seule origine : pas de CORS en production. Le build se fait avec l'adresse du backend, et le service worker est versionné pour qu'un déploiement remplace bien l'ancien cache. Vérifier que manifest.json (nom, icônes 192 et 512 px, display standalone, theme_color, start_url) est servi correctement.
flutter build web --dart-define=API_BASE_URL=https://mon-pc.tailXXXX.ts.net/api
Backend toujours prêt
Lancer automatiquement au démarrage de Windows : PostgreSQL, Ollama et le backend (uvicorn), par exemple via le Planificateur de tâches ou un service. Réglages d'alimentation : empêcher la mise en veille sur secteur, ou accepter que le PC dormant soit injoignable (le mobile reste alors en mode hors-ligne). Après une coupure de courant, tout doit redémarrer sans intervention.
Sécurité sans authentification applicative
Tout repose sur Tailscale et sur ton PC : règles d'accès (ACL) limitées à tes appareils personnels, partage de machine désactivé, pas de Funnel. PostgreSQL et Ollama écoutent seulement sur localhost. Pare-feu Windows actif. Si le téléphone est perdu : le retirer de la console Tailscale, et verrouiller l'écran du téléphone au quotidien. Si un jour d'autres personnes doivent utiliser l'app, il faudra ajouter une authentification.
Quand le PC est injoignable
PC éteint, en veille, sans Internet, ou Tailscale coupé sur le téléphone : l'API ne répond pas. Le mobile passe en mode hors-ligne, enregistre ses actions dans la file d'attente et se synchronise au retour du PC. Si la connexion directe entre les appareils est impossible, Tailscale passe par un relais : plus lent, mais fonctionnel.

Résolution des conflits

C. Protocole de synchronisation

Principe : l'appareil écrit d'abord en local et dans une file d'actions ; la synchronisation envoie la file puis récupère les changements. Un seul cycle à la fois ; déclenché au lancement, à la reprise de l'app, au retour du réseau, après chaque action si le PC est joignable, et par un bouton manuel.

POST /api/sync/push { "appareil_id": "android-7f3a", "operations": [ {"op_id": "b1c2…", "type": "mot.creer", "donnees": {"id": "9d4e…", "terme": "lowkey", "cree_le": "2026-10-12T08:14:00Z"}}, {"op_id": "c3d4…", "type": "revision.repondre", "donnees": {"revision_id": "a7b8…", "qualite": 4, "repondu_le": "2026-10-12T08:20:00Z"}} ] } → 200 {"resultats": [ {"op_id": "b1c2…", "statut": "applique"}, {"op_id": "c3d4…", "statut": "deja_applique"}]} GET /api/sync/pull?since=1284&limite=200 → 200 {"curseur": 1311, "a_suite": false, "changements": {"mots": […], "extraits": […], "revisions": […], "reglages": […], "artistes": […]}}
  1. Vérifier que le PC répond (/api/health, délai court) ; sinon rester en mode hors-ligne.
  2. Lire les actions en attente dans l'ordre de création.
  3. Les envoyer par lots de 50 à /sync/push ; le serveur applique chaque opération dans une transaction et enregistre son op_id dans sync_op ; rejouer une opération déjà appliquée renvoie « deja_applique ».
  4. Retirer de la file uniquement les opérations dont l'accusé est « applique » ou « deja_applique » ; une erreur 4xx définitive est déplacée dans une liste « à examiner » visible dans Réglages ; une erreur réseau ou 5xx laisse l'opération en file.
  5. Appeler /sync/pull avec le dernier curseur, répéter tant que a_suite est vrai, appliquer les changements au cache local, enregistrer le curseur.
  6. Les suppressions arrivent comme des lignes avec deleted_at renseigné.
  7. Conflits : réglages et champs modifiables, la modification la plus récente selon l'ordre serveur gagne ; réponses de révision, journal qui s'ajoute ; mot créé hors-ligne en double d'un mot du serveur (même terme_normalise) : fusion sur le mot existant.
  8. Base locale vide ou curseur inconnu du serveur : synchronisation complète (since=0).
  9. Mots créés hors-ligne : statut « en_attente » ; le serveur lance ensuite la recherche d'extrait, la traduction et l'explication, puis renvoie la fiche complète au prochain pull.

D. Algorithme de révision (SM-2 adapté)

Entrée : note de qualité q de 0 à 5. « Je ne savais pas » = 1, « Je savais » = 4, option « Facile » = 5 (facultative). Exercice de production : correct = 4, proche = 3, incorrect = 1. Valeurs initiales : repetitions = 0, facilite = 2,5, intervalle = 0. Le téléphone applique cet algorithme hors-ligne ; le PC rejoue les réponses dans l'ordre à la synchronisation et sa valeur fait foi.

si q < 3 : repetitions = 0 ; intervalle = 1 ; facilite inchangée sinon : si repetitions == 0 : intervalle = 1 si repetitions == 1 : intervalle = 3 sinon : intervalle = ceil(intervalle_precedent × facilite) repetitions += 1 facilite = max(1,3 ; facilite + 0,1 − (5 − q) × (0,08 + (5 − q) × 0,02)) date_prevue = date_de_reponse + intervalle jours

E. Prompts et règles pour l'IA

Modèle : Llama 3.1 8B via Ollama sur ton PC. Paramètres : température 0,2 ; réponse non diffusée en continu ; limite de génération 150 jetons pour l'explication ; délai d'attente 30 s ; une nouvelle tentative maximum.

Explication "Explique en français, en 2 phrases maximum, le sens de "{mot}" dans ce contexte : "{extrait}". Indique si c'est de l'argot ou une expression figurée. Ne cite pas d'autres paroles de chanson." Génération de phrase "Écris une phrase simple en français (12 mots maximum) utilisant le mot "{mot_fr}", dans un contexte différent de la chanson. Réponds par la phrase seule." Évaluation (sortie JSON demandée) "Phrase : {phrase_fr}. Traduction attendue : {ref_en}. Réponse de l'utilisateur : {reponse}. Réponds uniquement en JSON : {"verdict": "correct|proche|incorrect", "explication": "une phrase de 200 caractères maximum"}."

Validation : le JSON doit contenir un verdict dans la liste autorisée et une explication de 200 caractères maximum ; sinon une nouvelle tentative, puis repli par mots-clés : on normalise (minuscules, sans ponctuation) la réponse et la référence, et on calcule la part de mots de la référence présents dans la réponse : 70 % ou plus = correct, de 40 % à 70 % = proche, moins = incorrect. Le verdict de repli est marqué comme tel. Les sorties de l'IA sont toujours affichées comme « générées automatiquement ».
